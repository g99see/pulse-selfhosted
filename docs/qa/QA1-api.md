## D-1. Статистика привязывает чек-ин к дню создания, а не к `occurredAt` (задним числом — не тот день)  — Высокая

**Где:** `apps/api/src/stats/stats.service.ts` — выборка `prisma.checkIn.findMany({ where: { userId, createdAt: {...} } })` (стр. ~83) и бакетирование `bucket(dayKeyInTimezone(checkIn.createdAt, timezone))` (стр. ~121). То же в `moodCalendar` (стр. ~262) и `periodTotals` (стр. ~303): фильтр/ключ дня по `createdAt`.

**Шаги (пользователь, tz = Europe/Kyiv; «вчера» = 2026-10-15, «сегодня» = 2026-10-16):**
1. `POST /checkins {"mood":5}` → 201, `occurredAt = 2026-10-16T15:40:23Z` (сегодня).
2. `POST /checkins {"mood":1,"occurredAt":"2026-10-15T19:00:00Z"}` → 201, `occurredAt = 2026-10-15T19:00:00Z` (вчера 22:00 по Киеву, в пределах 24 ч).
3. Читаем срезы.

**Факт (вывод `battery4_stats.py`):**
```
GET /checkins/today                              -> dayKey 2026-10-16, ids [только сегодняшний]
GET /checkins?from=2026-10-15T00:00:00Z&to=...23:59:59.999Z -> [вчерашний]   (фильтр по occurredAt — ОК)
GET /stats/day?date=2026-10-16  -> checkins=2 avgMood=3
GET /stats/day?date=2026-10-15  -> checkins=0 avgMood=null
GET /stats/mood-calendar?month=2026-10 -> average 3, «настроение» стоит ТОЛЬКО на 2026-10-16
GET /stats/report?period=day&date=2026-10-15 -> checkins=0
GET /stats/report?period=day&date=2026-10-16 -> checkins=2 avgMood=3
```
**Ожидалось:** чек-ин с `occurredAt` = вчера должен попадать во «вчера» во всей статистике
(согласованно с `/checkins/today` и историей `/checkins`, которые уже считают по `occurredAt`).
**Факт:** он приписан к сегодня; вчерашний день пуст, а среднее настроение сегодня искажено
((5+1)/2=3 вместо 5).

**Влияние:** заполнение задним числом (ТЗ §3.3, ключевая фича) ломает все агрегаты —
дашборд дня, тепловую карту настроения, отчёты за период и корреляции (все читают `DailyStat`
/ фильтруют по `createdAt`). Пользователь, дописавший пропущенный чек-ин за вчера, видит его
не в тот день. Несогласованность легко наблюдается: один и тот же чек-ин виден в
`/checkins?from/to` за вчера, но отсутствует в статистике за вчера.

## D-2. `dayBoundsInTimeZone` неверно считает границы суток в дни перехода на летнее/зимнее время — Средняя

**Где:** `packages/shared/src/checkin.ts:163` `dayBoundsInTimeZone()`. Потребитель — единственный:
`apps/api/src/checkins/checkins.service.ts:168` (`GET /checkins/today`). Внутри смещение берётся
на **текущий момент** (`offset = Date.UTC(локальные y/m/d h:m:s) - date.getTime()`) и применяется
к полуночи, а конец суток жёстко `start + 24 ч`.

**Факт (`dst_verify.js`, сравнение с реальной локальной полуночью и с `zonedDayBounds` из `stats.ts`):**
```
Europe/Kyiv 2026-10-25 (переход назад, реальные сутки 25 ч):
  реально:            start=2026-10-24T21:00:00Z end=2026-10-25T22:00:00Z
  dayBoundsInTimeZone: start=2026-10-24T22:00:00Z end=2026-10-25T22:00:00Z  -> start НЕВЕРЕН (+1 ч), len 24 ч
  zonedDayBounds:      start=2026-10-24T21:00:00Z end=2026-10-25T22:00:00Z  -> OK

America/Los_Angeles 2026-11-01 (переход назад): start=08:00Z, реально 07:00Z -> +1 ч
Pacific/Auckland 2026-09-27 (переход вперёд, 23 ч): start=2026-09-26T11:00Z, реально 12:00Z -> -1 ч
Обычные дни — совпадают с реальными.
```
**Ожидалось:** границы локального дня пользователя (как в `zonedDayBounds`, итеративно — корректно).
**Факт:** в день перехода начало суток смещено на 1 час, а длина суток принудительно 24 ч
(на 25-часовом дне теряется первый локальный час 00:00–01:00, на 23-часовом — захватывается
последний час предыдущего дня).

**Влияние:** `GET /checkins/today` (карточка «Сегодня» на главной) в течение одного часа в день
перехода покажет неверный набор чек-инов; при этом `GET /stats/day` (через `zonedDayBounds`) для
того же локального дня даёт другой интервал — два эндпоинта противоречат друг другу.
`GET /checkins/goal` использует из этой функции только `dayKey` (корректен), поэтому не затронут.
Прим.: `packages/shared/src/habits.ts:82` тоже берёт только `dayKey` — не затронут.

## Замечания низкой важности (не блокеры; требований в доке нет)

- **N-1. Нет идемпотентности/дедупликации при создании.** 15 параллельных идентичных
  `POST /checkins {"mood":5,"note":"dup"}` → все 15 `201`, 15 уникальных id; 5 последовательных
  дублей → 5 записей. Двойной клик в UI создаст дубликаты чек-инов.
- **N-2. Нет ограничения частоты на чек-инах.** 60 быстрых `POST /checkins` подряд → 60×`201`
  (при том что, например, `/account/export` лимитируется — `RateLimitService` в коде есть).
- **N-3. HTML не санитизируется на API.** `note`/`tags` со `<script>alert(1)</script>` и
  `#<b>x</b>` сохраняются и возвращаются «как есть», в т.ч. в экспорте. Для web это, вероятно,
  безопасно (React экранирует), но стоит проверить экспорт/иные потребители (XSS-риск вне API-периметра).
- **N-4. Порог «сон только утром» считается по `occurredAt`, а не по «сейчас».** Вечером можно
  отправить `sleepHours`, указав `occurredAt` в утреннее окно (дозаполнение утра). Фронт в это
  время поле скрывает, поэтому через UI недостижимо; поведение спорное, но сломать данные нельзя.
- **N-5. Асимметрия допуска на границе задним числом.** Будущее допускается с запасом 60 с
  (`FUTURE_TOLERANCE_MS`), а `occurredAt` ровно -24 ч из-за сетевой задержки отвергается
  (`checkin_window_expired`); `-23ч59м59с` проходит. Мелочь, но клиент с небольшим расхождением
  часов может получить отказ на границе.

## Проверено — работает корректно

- **Границы полей** (`battery1.py`): `mood` 1–5 (0/6/3.5/"3"/null/пусто → `400 validation_error`);
  `energy`/`stress` 1–5 (0/6/2.5 → 400); `sleepHours` 0/24/7.5/23.99 → 201, -1/25 → 400;
  `water` целое 0–50 (51/-1/2.5/1e9 → 400); `steps` целое 0–200000 (200001/-1/1.5 → 400);
  теги: 20 шт → ок, 21 → 400, пустая строка → 400, 64 симв. → ок, 65 → 400, юникод/эмодзи → ок;
  `note`: 2000 → ок, **2001 и 10000 → 400** (в доке и схеме лимит 2000 — совпадает);
  `daySummary` 280 → ок, 281 → 400; `slot` ∈ {morning,day,evening}, иначе 400.
- **`occurredAt`**: будущее (+2 мин, +1 ч, +25 ч) → `400 validation_error`; старше 24 ч → `400
  checkin_window_expired`; в пределах 24 ч → 201; мусор/пусто → `400 validation_error`.
- **Окно сна по локальному часу** (`battery2_tz.py`) ровно на границах, для всех 4 зон:
  local 03:59 → `sleepHours` **обнуляется**, 04:00 → **сохраняется**, 11:59 → сохраняется,
  12:00 → обнуляется (Pacific/Auckland, America/Los_Angeles, Asia/Kolkata, Europe/Kyiv).
  Вне окна сон тихо игнорируется, остальные поля (`water`, `energy`, `stress`, `steps`) не страдают.
- **IDOR** (`battery3_auth.py`): чужой чек-ин → `404 checkin_not_found` для GET/PUT/DELETE;
  чужой список не содержит записей владельца; GET/PUT/DELETE несуществующего id → 404.
- **Аутентификация/CSRF**: без сессии GET → `401 unauthorized`; без CSRF-cookie/заголовка POST →
  `403 csrf_failed` (проверка CSRF идёт раньше аутентификации); неверный `X-CSRF-Token` →
  `403 csrf_failed`; PUT/DELETE без CSRF → `403 csrf_failed`.
- **Согласованность после правки/удаления** (`battery5_misc.py`): PUT меняет `mood` → `/stats/day`
  пересчитывается (avgMood 4→2); DELETE → checkins/avgMood уменьшаются; после удаления всех —
  `checkins=0, avgMood=null` (залежавшегося кеша `DailyStat` нет).
- **Корреляции при малых данных** (`battery5_misc.py`): 0 и 1 день данных → корректный ответ
  `enough:false, diffPercent:null`, без 500.
- **Экспорт содержит чек-ины**: `GET /account/export?format=json` → `counts.checkIns`, `data.checkIns`;
  `?format=csv` → ZIP (PK) с `check_ins.csv` и шапкой `id,user_id,mood,...,occurred_at,slot,steps,water`.
- **Фильтры/прочее**: `limit` 0/501/abc → 400, 1 → 200; `from=garbage` → 400; `from>to` → 200 (пусто);
  `goal` `perWeek` валидируется 1..21; расписание: несоответствие числа времён и дубли времён → 400,
  7 раз в день → 400; `GET /checkins/quick` → 201.
- **Парсер однострочного чек-ина** (`parser.js`, `parseCheckinLine`): результат всегда проходит
  `CheckInInputSchema`; `энергия 3.7`/`сон 30` → `{ok:false,error:'value'}`; `0/6/3.5/abc` → `error:'mood'`;
  `#СПОРТ`+`#спорт` → дедуп `["спорт"]`. Неcущественных дефектов не выявлено (путь Telegram, вне REST API).
