# Фаза 1 — эксплуатация: мастер первого запуска, бэкап и восстановление

Документ закрывает пробелы Фазы 1 по ТЗ: **§6 «Надёжность»**, **§9 п.7**
(роли и режим регистрации) и **§10 «Развёртывание»** (мастер первого запуска,
бэкап по расписанию, восстановление одной командой, миграции перед обновлением).

## 1. Мастер первого запуска и роли

### API

| Метод | Путь | Назначение |
| ----- | ---- | ---------- |
| `GET`  | `/api/setup/status` | `{ needsSetup, registrationMode }`; `needsSetup = true`, пока в БД нет ни одного пользователя |
| `POST` | `/api/setup` | Создаёт первого пользователя с ролью `admin` (требует CSRF, как и любой мутирующий запрос) |

- Первый администратор создаётся с уже подтверждённым email: на пустом инстансе
  без настроенного SMTP иначе мастер заблокировал бы сам себя.
- Эндпоинт **блокируется навсегда**, как только в БД появляется пользователь:
  повторный вызов отвечает `409 setup_completed`.
- Гонка двух одновременных `POST /api/setup` разрешается транзакционной
  advisory-блокировкой PostgreSQL (`pg_advisory_xact_lock`) и повторной проверкой
  счётчика внутри транзакции — создаётся ровно один администратор.
  Это покрыто интеграционным тестом `apps/api/test/setup.integration.test.ts`.

### Роли

Поле `User.role` (миграция `20261001134748_user_roles`): `user | moderator | admin`.
Существующие пользователи получают значение по умолчанию `user`; первый
администратор из мастера — `admin`. Роль возвращается в `PublicUser.role`.

### Режим регистрации

`InstanceSettings.registrationMode` (единственная строка `id = 'instance'`):
`open` (по умолчанию) | `invite` | `closed`.

| Режим | Поведение `POST /api/auth/register` |
| ----- | ----------------------------------- |
| `open`   | регистрация разрешена |
| `invite` | `403 registration_invite_required` (механизм приглашений появится позже) |
| `closed` | `403 registration_closed` |

Строки настроек может не быть — тогда режим считается `open`, поэтому поведение
существующих инсталляций не меняется.

### UI

- Страница `/setup` — форма создания администратора. Если инстанс уже настроен,
  показывает «Сервер уже настроен» со ссылкой ко входу.
- Компонент `SetupGuard` на лендинге и странице входа: если `needsSetup = true`,
  клиент переводит пользователя на `/setup` (проверка на клиенте — лендинг
  остаётся статическим, а недоступный API не ломает страницу).
- Тексты — только в `apps/web/src/lib/i18n.ts` (ru/en).
- E2E: `apps/web/e2e/setup.spec.ts` — редирект с логина, создание администратора
  (с подменой ответов API, т.к. e2e-БД общая), экран «уже настроено» и проверка,
  что живой `POST /api/setup` закрыт после первого администратора.

## 2. Бэкап

`scripts/backup.sh` (POSIX `sh`, работает в двух режимах):

- **local** — внутри контейнера `backup` / на хосте с клиентом PostgreSQL:
  `pg_dump` напрямую по `PGHOST`;
- **compose** — на хосте без `psql`: `docker compose exec postgres pg_dump`.

Режим задаётся `BACKUP_MODE` или определяется автоматически. Результат —
`./backups/backup-<UTC>.tar.gz` с содержимым:

- `dump.pgc` — дамп в custom-формате (`pg_dump -Fc`);
- `metadata.json` — `createdAt`, `database`, **`migration`** (последняя применённая
  миграция Prisma), `pgVersion`, `appVersion`.

Ротация: хранятся `BACKUP_KEEP` (по умолчанию 7) последних архивов. После
успешного бэкапа создаётся маркер `./backups/.last-success`.

Сервис `backup` в `docker-compose.yml` (образ `postgres:16-alpine`) запускает
`backup.sh --daemon`: бэкап сразу при старте, затем раз в `BACKUP_INTERVAL_HOURS`
(24 часа). Healthcheck проверяет, что маркер свежий (не старше двух интервалов).

Каталог `./backups` добавлен в `.gitignore`.

## 3. Восстановление одной командой

```bash
scripts/restore.sh backups/backup-<UTC>.tar.gz
```

Порядок: распаковка архива → чтение версии схемы из `metadata.json` → сравнение
с последней применённой миграцией целевой БД. При расхождении (и если обе версии
определены) скрипт останавливается; повтор с `--force`, если решение осознанное.
Затем `pg_restore --clean --if-exists --no-owner --no-privileges`. Флаг `--migrate`
после восстановления накатывает миграции текущего образа (`prisma migrate deploy`).

## 4. Обновление

```bash
scripts/upgrade.sh
```

Порядок: **бэкап** → `docker compose pull` (при неудаче — `build`) → `docker compose up -d`.
Миграции Prisma применяет контейнер `api` при старте (CMD в `apps/api/Dockerfile`).
Пропустить бэкап можно только явно: `SKIP_BACKUP=1`.

## 5. Переменные окружения

Добавлены в `.env.example` и/или проброшены в `docker-compose.yml`:

- эксплуатация: `PUBLIC_ORIGIN`, `PUBLIC_API_URL`, `APP_VERSION`,
  `BACKUP_INTERVAL_HOURS`, `BACKUP_KEEP`, `POSTGRES_*`;
- почта и push: `SMTP_URL`, `MAIL_FROM`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`,
  `VAPID_SUBJECT`; подписка web-push — в настройках приложения;
- секреты и интеграции: `APP_ENCRYPTION_KEY`, `GOOGLE_CLIENT_ID`,
  `GOOGLE_CLIENT_SECRET`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`,
  `RATES_PROVIDER`.

## 7. Ограничения

- Режим `invite` пока работает как «закрыто»: механизм приглашений — отдельная
  задача. Код ошибки отличается (`registration_invite_required`).
- UI управления `registrationMode` (переключатель в настройках администратора)
  не входит в эту задачу; значение задаётся в БД/будущем экране настроек.
- Бэкап охватывает базу данных; файловый том приложения появится вместе с
  загрузкой файлов (сейчас в Фазе 1 пользовательских файлов нет).
