# Резервные копии и откат миграций

Страница про то, как вернуть данные и схему БД назад. Про сам бэкап и
восстановление целиком — в разделе [«Администрирование»](/admin/#резервное-копирование);
здесь — откат **одной миграции** схемы (ТЗ v2 §8).

## Когда нужен откат

Обновление принесло миграцию, а новая версия работает неправильно, и вы
возвращаетесь на предыдущий образ. Образ старой версии не знает про новые
колонки и таблицы, но они не мешают; откат нужен, если миграция ломает работу
или вы хотите убрать её следы.

::: warning Данные удаляемых таблиц и колонок теряются
Откат откатывает **схему**. Скрипт сам снимает бэкап перед откатом — по нему
можно вернуть всё как было (`scripts/restore.sh`).
:::

## У каждой миграции v2 есть down.sql

Рядом с `migration.sql` лежит `down.sql` — обратные команды:

| Миграция | Что откатывает | Что теряется |
| --- | --- | --- |
| `20261002120000_import_amount_base` | ничего (заполнение данных) | — |
| `20261006120000_notifications_v2` | таблицы доставок, Discord, настройки каналов; `telegram_links.blocked_at`; возвращает пустую `push_subscriptions` | журнал доставок, привязки Discord; подписки web push не восстанавливаются |
| `20261006130000_checkin_full` | `check_in_drafts`, средние `avg_energy/avg_stress/avg_sleep` | средние (пересчитаются при накате) |
| `20261006140000_reconciliation` | `account_bank_balances`, `external_id/bank_time/bank_balance` | данные сверки |
| `20261006150000_statement_mismatch_notified` | отметка уведомления о расхождении | отметки |
| `20261006160000_checkin_goal` | цель чек-инов у пользователя | цели |
| `20261006170000_day_summary_link` | таблица ссылок «Итог дня» | ссылки |
| `20261007100000_remove_social` | пересоздаёт **пустые** таблицы соцсети, `users.profile_visibility`, `goals.visibility` | данные соцсети уже удалены миграцией — вернуть можно только из бэкапа **до** неё |

## Скрипт отката

```bash
scripts/migrate-rollback.sh 20261006170000_day_summary_link
```

Единственный обязательный аргумент — **имя каталога миграции** из
`apps/api/prisma/migrations`. Что делает скрипт:

1. Проверяет, что миграция применена и **она последняя** из применённых.
   Откатывать нужно от новых к старым; обойти проверку — флагом `--force`.
2. Просит подтверждение (`--yes` — без вопроса).
3. Снимает бэкап через `scripts/backup.sh`. Не получилось — откат не идёт.
4. Одной транзакцией через `docker compose exec postgres psql` применяет
   `down.sql` и помечает миграцию откаченной (`rolled_back_at` в
   `_prisma_migrations` — то же, что делает `prisma migrate resolve
   --rolled-back`). Ошибка — транзакция отменяется, схема остаётся прежней.
   После этого следующий `prisma migrate deploy` (его делает `upgrade.sh` и
   контейнер api при старте) накатит миграцию заново.

Проверено на копии рабочей базы: бэкап → откат → повторное применение.
Переменная `PGDATABASE` выбирает базу (по умолчанию `puls`) — так откат можно
сначала отрепетировать на копии.

Несколько миграций откатываются по одной, от новой к старой:

```bash
scripts/migrate-rollback.sh 20261006170000_day_summary_link --yes
scripts/migrate-rollback.sh 20261006160000_checkin_goal --yes
```

Настройки: `PGUSER`, `PGDATABASE` (по умолчанию `puls`), `COMPOSE_PROJECT`.
Имя миграции допускает только латиницу, цифры и `_` — путь вида `../x`
отклоняется.

::: tip После отката
Верните образ `api` предыдущей версии и перезапустите: `docker compose up -d`.
Если оставить новый образ, при старте он снова применит откаченную миграцию.
:::

## Метрики и логи

- `GET /api/admin/metrics` (роль admin; в вебе — «Метрики» в меню) отдаёт число
  доставок по статусам и каналам, длину очереди, ошибки с запуска и время
  последнего тика планировщика.
- Каждый ответ API несёт `X-Request-Id` (входящий безопасный id сохраняется).
  Ошибки 5xx пишутся в stdout одной JSON-строкой с `requestId`, методом,
  путём без query и стеком — их легко искать по id из ответа.
