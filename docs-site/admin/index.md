# Администрирование экземпляра

Эта страница — для владельца self-hosted экземпляра «Пульса»: мастер первого
запуска, роли, режим регистрации, резервные копии и обновление.

Основана на `docs/PHASE1-OPS.md`.

## Мастер первого запуска

На пустом экземпляре сервис предлагает создать первого администратора:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/setup/status` | `{ needsSetup, registrationMode }`; `needsSetup = true`, пока в БД нет ни одного пользователя |
| `POST` | `/api/setup` | Создаёт первого пользователя с ролью `admin` (требует CSRF) |

- Первый администратор создаётся с уже подтверждённым email — иначе на пустом
  инстансе без настроенного SMTP мастер заблокировал бы сам себя.
- После появления первого пользователя эндпоинт закрывается навсегда: повторный
  `POST /api/setup` отвечает `409 setup_completed`.
- Гонка двух одновременных `POST /api/setup` разрешается транзакционной
  advisory-блокировкой PostgreSQL (`pg_advisory_xact_lock`): создаётся ровно
  один администратор.

В браузере мастер живёт на странице `/setup`; компонент `SetupGuard` на лендинге
и странице входа переводит туда, пока `needsSetup = true`.

## Роли

Поле `User.role` (миграция `20261001134748_user_roles`):

| Роль | Значение | Что даёт |
| --- | --- | --- |
| Пользователь | `user` | Обычный аккаунт (значение по умолчанию) |
| Админ | `admin` | Роль первого пользователя из мастера; полный доступ |

Роль возвращается в `PublicUser.role`. На API доступ ограничивается `RolesGuard` вместе с
декоратором `@Roles(...)`.

## Режим регистрации

Режим хранится в `InstanceSettings.registrationMode` (единственная строка
`id = 'instance'`):

| Режим | Значение | Поведение `POST /api/auth/register` |
| --- | --- | --- |
| Открытая регистрация | `open` (по умолчанию) | Регистрация разрешена |
| По приглашениям | `invite` | `403 registration_invite_required` |
| Один пользователь | `closed` | `403 registration_closed` |

Если строки настроек нет, режим считается `open` — поведение существующих
инсталляций не меняется.

::: warning Ограничение
Отдельного экрана-переключателя режима регистрации пока нет: значение задаётся
в БД (`InstanceSettings`). Режим `invite` ведёт себя как «закрыто» — сам механизм
приглашений ещё не реализован (отличается только код ошибки).
:::

## Общий AI-ключ экземпляра и учёт токенов

> **AI-помощник и общий ключ экземпляра реализованы.** Подробности — на странице [AI-помощник](/ai/).

По ТЗ §7 экземпляр хранит общий AI-ключ и его параметры в `InstanceSettings`
(провайдер, зашифрованный общий ключ, модель, лимит токенов на пользователя в
месяц), а учёт — в сущностях `UserAiKey` (личный ключ, тоже зашифрованный) и
`AiUsage` (пользователь, месяц, токены, стоимость). Секреты шифруются
AES-256-GCM мастер-ключом `APP_ENCRYPTION_KEY`; новых переменных окружения под AI
не вводилось.

## Резервное копирование

`scripts/backup.sh` снимает дамп PostgreSQL в custom-формате и складывает в архив:

```bash
# Резервная копия вручную
scripts/backup.sh
```

Скрипт работает в двух режимах (задаётся `BACKUP_MODE` или определяется сам):

- **local** — внутри контейнера `backup` / на хосте с клиентом PostgreSQL:
  `pg_dump` напрямую по `PGHOST`;
- **compose** — на хосте без `psql`: `docker compose exec postgres pg_dump`.

Результат — `./backups/backup-<UTC>.tar.gz` с содержимым:

| Файл | Что внутри |
| --- | --- |
| `dump.pgc` | Дамп в custom-формате (`pg_dump -Fc`) |
| `metadata.json` | `createdAt`, `database`, `migration` (последняя применённая миграция Prisma), `pgVersion`, `appVersion` |

Ротация: остаются `BACKUP_KEEP` последних архивов. После успешного бэкапа
создаётся маркер `./backups/.last-success`. Каталог `./backups` добавлен в
`.gitignore`.

Сервис `backup` в `docker-compose.yml` (образ `postgres:16-alpine`) запускает
`backup.sh --daemon`: бэкап сразу при старте, затем раз в `BACKUP_INTERVAL_HOURS`.
**Healthcheck** сервиса проверяет свежесть маркера — он не должен быть старше
двух интервалов.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `BACKUP_DIR` | Каталог архивов | `./backups` |
| `BACKUP_KEEP` | Сколько архивов хранить | `7` |
| `BACKUP_PREFIX` | Префикс имени архива | `backup` |
| `BACKUP_INTERVAL_HOURS` | Интервал в сервисе `backup` | `24` |
| `BACKUP_MODE` | `local` или `compose` | автодетект |
| `COMPOSE_PROJECT` | Отдельный compose-проект | — |
| `PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE` | Доступ к БД | `PGDATABASE=puls` |

Откат одной миграции схемы — [Бэкапы и откат миграций](/ops/backup).

## Восстановление одной командой

```bash
scripts/restore.sh backups/backup-<UTC>.tar.gz
```

Порядок: распаковка архива → чтение версии схемы из `metadata.json` → сравнение
с последней применённой миграцией целевой БД. При расхождении скрипт
останавливается; если решение осознанное — повтор с `--force`.

```bash
# Восстановить, даже если версия схемы в БД не совпадает с архивом
scripts/restore.sh backups/backup-....tar.gz --force

# После восстановления применить миграции текущего образа
scripts/restore.sh backups/backup-....tar.gz --migrate
```

Данные восстанавливаются через `pg_restore --clean --if-exists --no-owner
--no-privileges`.

## Обновление

```bash
scripts/upgrade.sh
```

Порядок: **бэкап** → `docker compose pull` (при неудаче — `build`) →
`docker compose up -d`. Миграции Prisma применяет контейнер `api` при старте.
Пропустить бэкап можно только явно: `SKIP_BACKUP=1`.

## Страница состояния

- `/health` — эндпоинт API; у каждого контейнера compose есть healthcheck и
  автоперезапуск.
- `docker compose ps` — состояние сервисов (в конце `scripts/upgrade.sh`
  выводится автоматически).
- `docker compose ps backup` — сервис бэкапа должен быть `healthy`; `ls backups/`
  показывает архивы.
